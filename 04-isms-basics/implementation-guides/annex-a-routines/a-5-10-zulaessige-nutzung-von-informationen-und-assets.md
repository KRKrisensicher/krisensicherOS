# A.5.10 — Acceptable use of information and assets

## Purpose

Acceptable use of information and assets makes clear how people, service providers, and technical roles may handle information, devices, applications, cloud services, data repositories, communication tools, and supporting assets. The goal is not a long list of prohibitions, but actionable rules for everyday work, exceptions, and escalation.

The core is an understandable usage routine: Which use is allowed, which needs approval, which is prohibited, how are special cases decided, and how is effectiveness checked?

## Control objective in repository language

The organization operates a traceable routine for acceptable use. Rules for information and assets are formulated appropriately for roles and risks, communicated, embedded in onboarding and operations, updated when changes occur, and connected with exceptions, violations, awareness, access, and asset inventory.

## Typical risks

- If usage rules are unclear, employees use unapproved tools, private repositories, or insecure transmission paths.
- If information is used without connection to protection need, data leakage, misdirected sending, or unauthorized sharing may result.
- If external staff or service providers do not know the rules, shadow processes and uncontrolled access arise.
- If exceptions remain informal, insecure practices become permanent.
- If rules are too abstract, they do not help in everyday work and are ignored.
- If violations are only sanctioned but not analyzed, the organization does not learn from misuse, tool gaps, or target conflicts.

## Triggers

- entry, role change, departure, or commissioning of external staff.
- new asset, new tool, new data set, new data class, new cloud/SaaS use, or new form of communication.
- project, change, procurement, or supplier change.
- security event, misdirected sending, policy violation, phishing case, or audit finding.
- change in work model, home office, mobile work, bring-your-own-device, or private use.
- review of asset inventory, access, awareness, or data protection/legal requirements.
- management decision on accepted use, productivity, control, or exceptions.

## Roles and responsibilities

- **ISMS owner / security role:** defines usage logic, minimum rules, exception process, and review.
- **Information owner / asset owner:** defines business use, protection need, and restrictions for information and assets.
- **IT/platform owner:** provides approved tools, technical guardrails, configurations, and support paths.
- **HR / people function:** integrates usage rules into onboarding, role changes, and offboarding.
- **Managers:** ensure transfer into daily work, clarification of target conflicts, and follow-up in teams.
- **Data protection / legal:** reviews personal data, private use, monitoring, employee data, contractual and legal questions.
- **Management:** decides exceptions, resources, tool approvals, and accepted residual risks.

## Implementation

### Minimum start

Goal: communicate critical usage rules clearly and make exceptions steerable.

1. The organization names the most important information and assets in scope: data repositories, devices, email/chat, cloud services, customer information, admin tools.
2. Short rules are formulated for these areas: allowed, only with approval, not allowed, ask when unsure.
3. Rules are communicated during onboarding and relevant role changes.
4. A simple exception and approval path exists for new tools, external sharing, private use, or special access.
5. Security events and violations are not only documented, but checked for rule, tool, or training gaps.
6. Rules are updated at least annually or when significant changes occur.

Minimum evidence:

- compact usage rule or role briefing,
- communication or onboarding evidence,
- approval/exception tickets,
- review note on changes,
- lessons learned from violations or misuse.

### Solid practice

Goal: acceptable use is connected with roles, data classes, and asset types.

1. Usage rules distinguish asset types: information, endpoints, mobile devices, SaaS/cloud, communication channels, removable media, printing, admin tools, AI tools.
2. Rules are connected with data classes, protection needs, access, and asset owners.
3. Approved tools and permitted data repositories are made visible so secure use is practical.
4. Exceptions include rationale, duration, compensation, owner, and follow-up date.
5. External staff and service providers receive suitable usage rules and return obligations.
6. Awareness and manager briefings cover typical everyday situations.
7. Violations, misdirected sending, and shadow IT are evaluated as input for improvement.

Strong evidence:

- role- and asset-related usage rules,
- approved tool and data repository catalog,
- communication and confirmation evidence,
- exception and approval log,
- measures from violations or shadow-IT findings,
- review with data protection/legal and management points.

### Advanced practice

Goal: acceptable use is supported by technical guardrails, culture, and effective reviews.

1. Usage rules are embedded in tool approval, DLP/CASB logic, endpoint configuration, MDM, access control, and data classification, where appropriate.
2. Teams receive context-specific playbooks: secure customer communication, file exchange, mobile work, admin tasks, AI use, external collaboration.
3. Anomalies from monitoring, incident response, helpdesk, data-loss cases, or shadow IT are reviewed based on risk.
4. Technical controls are reviewed with data protection, employee representation, and legal when personal data evaluations arise.
5. Management receives decision-ready information about recurring target conflicts: missing secure tools, unclear data classification, productivity pressure, accumulation of exceptions.
6. Rules are improved so that they enable actual work and reduce risky workarounds.

## Routine flow

1. **Usage context emerges:** new person, new tool, new data set, new role, project, or exception need.
2. **Apply rule:** determine allowed use, approval need, or prohibition based on asset type, data class, and role.
3. **Obtain approval:** document decision for special use, external sharing, unapproved tool, or private use.
4. **Enable use:** provide approved tools, guidance, access, and secure alternatives.
5. **Record evidence:** document communication, confirmation, exception, approval, or rejection.
6. **Handle deviations:** triage violation, misuse, or shadow IT, analyze causes, and define measures.
7. **Perform review:** regularly review rules, exceptions, incidents, and tool needs.
8. **Improve:** adjust usage rules, awareness, technical guardrails, or management decisions.

## Decisions

- Which use is allowed by default, which needs approval, and which is excluded?
- Which data classes may be processed through which channels, tools, or devices?
- How are external staff, service providers, private use, and mobile work regulated?
- Who may approve exceptions and how long do they apply?
- Which technical controls are appropriate and need data protection/employment-law clarification?
- When does a violation indicate individual misconduct, and when does it indicate an unusable rule or missing tool?

## Evidence

### Strong evidence

- current usage rules with owner, scope, and review date,
- communication, onboarding, or confirmation evidence,
- approved tool and data repository catalog,
- exception decisions with duration and compensation,
- evidence of return, revocation, or change during role change/departure,
- lessons learned from violations, misdirected sending, or shadow IT,
- management decision for target conflicts or recurring exceptions.

### Weak evidence

- long policy without everyday situations or examples,
- signed usage policy without evidence of timeliness,
- tool list without data-class or approval connection,
- blanket prohibitions although no secure alternative is available,
- violations without root-cause analysis,
- awareness slide without evidence that relevant roles were reached.

### Evidence gaps

- no rule for cloud/SaaS or AI tool use,
- external staff not included,
- no exception or approval routine,
- private use or mobile work unclear,
- no connection to data classification and asset inventory,
- no tracking of recurring violations,
- technical controls without data protection/legal clarification.

## Effectiveness review

Review questions:

- Can employees and external participants identify which use is allowed and when they must ask?
- Are there secure, practical alternatives to prohibited or risky usage paths?
- Are exceptions time-limited, justified, and reviewed?
- Are new tools, data classes, and work models reflected in the rules?
- Do violations lead to root-cause analysis and improvement?
- Are data protection, legal, and employee-representation topics clarified for controls?

Possible metrics:

- share of target groups with current usage briefing,
- number of open or overdue exceptions,
- recurring violations by topic,
- shadow-IT findings with decision,
- time to approval or rejection of new tools,
- share of critical data classes with clear usage rules.

## BSIG/NIS2 connection point

Acceptable use is connectable to NIS2-oriented cyber hygiene, access protection, risk management, training, incident prevention, supply-chain security, and management oversight. For affected organizations, the concrete connection should be assessed in the requirements register, data classification, awareness, and asset governance.

This artifact does not replace legal, data protection, or employment-law assessment.

## Boundaries

- This artifact is not a complete work policy, data protection notice, or works agreement.
- It does not replace legal, data protection, or co-determination review for monitoring, private use, or personal data evaluation.
- It provides no certification, conformity, or security guarantee.
- It contains no licensed standards text.
- Usage rules must not only prohibit; they must enable secure work.

## Handoffs

- **HR handoff:** onboarding, role change, departure, external staff, confirmations, and return.
- **Data protection/legal handoff:** personal data, private use, monitoring, contractual questions, employee representation.
- **Asset/information owner handoff:** protection need, data class, allowed processing, and approval decision.
- **IT/platform handoff:** approved tools, technical guardrails, device configuration, support paths.
- **Incident handoff:** misdirected sending, data leakage, unauthorized use, compromised asset, or suspected misuse.
- **Management handoff:** recurring exceptions, missing secure alternatives, productivity/security conflicts.
- **Audit/evidence handoff:** missing communication evidence, outdated rules, or non-traceable exceptions.

## Typical mistakes

- Usage rules are so general that nobody can decide concrete everyday situations.
- Prohibitions are issued without providing approved alternatives.
- External staff, service providers, or mobile work are forgotten.
- Exceptions become permanent because no expiry date is set.
- Rule violations are assessed only individually although process or tool gaps are behind them.
- Monitoring is introduced without clarifying data protection, legal, or co-determination questions.
- AI, cloud, and collaboration tools are not included in the usage logic in time.

## Fictional mini example

A fictional consulting team wants to share customer documents through a new collaboration tool. The usage rule says: confidential customer data only through approved repositories; new tools need approval. The team lead creates an approval ticket. IT checks security functions, data protection is involved because of personal data content, and the information owner decides that the tool may be used only after MFA and retention are clarified. Until then, an approved data repository is used.

Evidence:

- usage rule for confidential information,
- approval ticket for the new tool,
- data protection and IT review note,
- decision by the information owner,
- communicated interim solution,
- follow-up for tool approval.
