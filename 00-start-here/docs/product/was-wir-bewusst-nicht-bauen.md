# What we deliberately do not build

## Purpose

This product guideline protects krisensicherOS from feature creep, false assurance, and consulting optics. The repo is intended to enable organizations to operate security governance themselves. It is not intended to recreate a cheap consulting library.

## Product rule

krisensicherOS implements only building blocks that support at least one of the following goals:

- increase decision readiness,
- clarify responsibility, roles, or human gates,
- create evidence flows from real work,
- enable repeatable operating routines,
- limit and make verifiable secure agent/AI use,
- reduce workload instead of creating new form-filling work.

Anything that only creates document volume, consulting optics, or false assurance stays out.

## Do not build

### No replication of standard texts

We do not build a hidden copy of ISO, DIN, EVS, BSI, or any other standards. The repo contains no licensed standard texts, control texts, tables, or factual substitute texts.

Instead, krisensicherOS provides:

- register structures,
- mapping fields,
- decision logic,
- evidence and review paths,
- references to license-compliant external sources.

### No false assurance packages

We do not build artifacts with marketing promises such as faster regulatory fulfillment, ISO readiness without review, passed audits, legal protection, or certification capability.

krisensicherOS prepares work. Compliance, legal, data protection, risk, and management decisions remain with accountable humans.

### No template mass without operating logic

We do not build a collection of generic policies, checklists, or tables that only multiply documents.

A template is only useful if it is clear:

- who uses it,
- when it is used,
- which decision or routine it supports,
- what evidence results from it,
- who reviews or approves it.

### No agent flood as an entry point

Agents, skills, and workflows are a toolkit, not a required entry point. New users should start with the 5-artifact quick start and only then activate additional building blocks.

New agents or skills are added only if they create a new operational capability that is not cleanly covered by existing building blocks.

### No AI magic without control logic

We do not build promises that AI takes over compliance, risk acceptance, legal assessment, or management decisions.

AI may:

- structure,
- summarize,
- flag gaps,
- suggest questions,
- prepare drafts.

AI must not:

- assume responsibility,
- process standard texts without a license,
- use real data without approval,
- make risk acceptance decisions,
- claim effectiveness,
- confirm compliance.

### No industry packages without reusability

Before v1.0, we do not build industry-specific special packages if they are only variants of existing operating logic. Industry and organization-specific characteristics belong in user-owned registers, examples, or extensions.

### No consulting PowerPoint language

We do not build methodological prose that is not translated into concrete work. Every artifact must have operational connectivity: role, routine, evidence, decision, review.

## What good extensions must satisfy

A new extension is suitable for v1.0 if it answers all questions:

1. Which concrete work does it make easier?
2. Which role uses the building block?
3. Which decision, evidence, or routine is created?
4. Which existing building block is not sufficient for this?
5. Which human gates and boundaries apply?
6. How does the extension prevent additional bureaucracy?

## Market logic

krisensicherOS does not replace high-quality consulting. It devalues poor consulting:

- copy-paste policies,
- generic gap lists,
- audit theater,
- unclear document packages,
- sorting work without decision value.

Good consulting remains valuable where organizations need architecture, prioritization, conflict resolution, management alignment, exercises, crisis readiness, and difficult risk decisions.
